# Alembic Q&A

---

## Q: What components work together to connect the app to the database?

Five components work together in a chain:

```
.env  →  config.py  →  database.py  →  get_db()  →  router/service
```

**`.env` / `config.py`** — holds the `DATABASE_URL` string (`postgresql+asyncpg://...`). `config.py` reads it via pydantic-settings and exposes `settings.database_url`.

**`database.py`** — uses that URL to create two things:
- `engine` — the connection pool (shared across the whole process, created once at startup)
- `AsyncSessionLocal` — a factory for creating sessions bound to that engine

**`get_db()`** — a FastAPI dependency (async generator). Each request calls it, gets a fresh `AsyncSession`, and the session is closed when the request finishes. This is the object your services receive as `db`.

**`Depends(get_db)` in the router** — wires it all together. FastAPI sees `db: AsyncSession = Depends(get_db)` and calls `get_db()` for every request automatically.

The driver doing the actual TCP work is **`asyncpg`** — that's what `postgresql+asyncpg://` in the URL tells SQLAlchemy to use.

## Q: Was `0001_initial_schema.py` written by hand or generated by Alembic? I thought we only need to configure the models and Alembic generates the migration.

It was **written by hand** — using raw SQL via `op.execute()` instead of Alembic's autogenerate.

You're right that Alembic can generate migrations from your models. The correct workflow is:

```bash
# Alembic compares your models against the current DB state and writes the migration
alembic revision --autogenerate -m "initial schema"

# Then apply it
alembic upgrade head
```

For autogenerate to work, `alembic/env.py` must import all your models and point `target_metadata = Base.metadata` at them — which our `env.py` already does correctly:

```python
from app.models import user, account, ledger_entry, transfer  # noqa: F401
target_metadata = Base.metadata
```

The reason the first migration was hand-written is that autogenerate has limitations — it cannot detect:
- `CHECK` constraints (e.g. `amount > 0`, `debit_account_id != credit_account_id`)
- Partial unique indexes (e.g. `WHERE user_id IS NULL`)
- Custom `DEFAULT` expressions (e.g. `gen_random_uuid()`)

Those would be missing or wrong in the autogenerated output and would need manual patching anyway.

**The tradeoff:**
| Approach | When to use |
|----------|-------------|
| `--autogenerate` | Routine changes — add a column, add a table. Fast, but always review the output. |
| Hand-written | Complex initial schema with constraints, partial indexes, custom defaults. Full control. |

For all future migrations (adding columns in Phase 2, new tables in Phase 3) use `alembic revision --autogenerate` and then review and patch what it missed.

## Q: When is `alembic/env.py` used?

`alembic/env.py` is the configuration script Alembic runs **every time you execute any `alembic` command** — `upgrade`, `downgrade`, `revision --autogenerate`, `current`, etc.

Think of it as Alembic's bootstrap file. Before it can do anything with the database, it needs to know how to connect and what your schema looks like. `env.py` answers both.

### What each part does

```python
from app.models import user, account, ledger_entry, transfer  # noqa: F401
target_metadata = Base.metadata
```
Imports your models so `Base.metadata` knows about all your tables. Without these imports, autogenerate would see an empty schema and think every table needs to be created (or dropped).

```python
async def run_migrations_online() -> None:
    connectable = create_async_engine(settings.database_url)
    async with connectable.connect() as connection:
        await connection.run_sync(do_run_migrations)
```
Creates a DB connection using your app's `DATABASE_URL` and applies the migrations. This is the path taken when you run `alembic upgrade head` normally.

```python
def run_migrations_offline() -> None:
    context.configure(url=settings.database_url, ...)
```
The offline path — generates SQL to stdout without connecting to the DB. Used when you want to produce a `.sql` file to hand to a DBA rather than running migrations directly.

### When each path runs

```
alembic upgrade head              →  online   (connects, applies migrations)
alembic downgrade -1              →  online
alembic revision --autogenerate   →  online   (connects to diff DB state vs models)
alembic upgrade head --sql        →  offline  (prints SQL, no connection needed)
```

### Why this `env.py` looks non-standard

The default `env.py` Alembic generates uses a synchronous connection. Since this project uses `asyncpg` (an async driver), a sync connection would fail. The custom `env.py` wraps everything in `asyncio.run()` to bridge that gap — that's the only reason it looks more complex than the Alembic default.

## Q: Why do we create a new session for each operation instead of sharing one session across the app?

**App-wide session is catastrophically wrong** — it causes security leaks, concurrency bugs, and memory leaks.

SQLAlchemy sessions are **not thread-safe or async-safe**. A shared session means:
- User A's loaded objects (in the identity map) are visible to user B
- Concurrent requests corrupt session state
- One request's DB error poisons all future requests
- No transaction boundaries — can't rollback one request without affecting others
- Memory leak — identity map accumulates every object ever loaded

### The correct pattern: session-per-operation

| Context | Session scope | Why |
|---------|--------------|-----|
| **FastAPI** | Session-per-request | One HTTP request = one business transaction. [[session-per-request]] |
| **Worker** | Session-per-operation | DB operations separated by network I/O. [[session-per-operation]] |

#### FastAPI: session-per-request
```python
# Request 1: POST /transfer (user A)
async with AsyncSessionLocal() as session:  # NEW session
    await handle_request(session)
    await session.commit()
# session closed, connection returned to pool

# Request 2: POST /transfer (user B)
async with AsyncSessionLocal() as session:  # DIFFERENT session
    await handle_request(session)
```

The `get_db()` dependency enforces this — FastAPI creates a new generator per request.

#### Worker: session-per-operation
```python
# claim_batch: lock rows → commit → release locks (milliseconds)
async with session_factory() as db:
    claimed = await claim_batch(db)
# session closed

# Kafka publish (no DB, no session needed)
await publish_to_kafka(claimed)

# confirm_batch: update status → commit (milliseconds)
async with session_factory() as db:
    await confirm_batch(db, claimed)
# session closed
```

Each DB operation gets a fresh session. Lock discipline is automatic — can't hold locks across network I/O by mistake.

### Why connection pooling makes this cheap

The `engine` maintains a connection pool (10 base + 20 overflow in our config). Each `async with session_factory()` borrows from the pool and returns it on exit. No TCP handshake per operation — overhead is negligible.

**NEVER share a session** across requests or operations. Always use request or operation scope.
